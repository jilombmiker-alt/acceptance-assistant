# PDF 与 Codex 交接的复检关联

日期：2026-09-16。本地验证已完成；代码已发布到 GitHub（30bcb01），魔搭部署仍待完成。

用户在同一目录修改代码、按原标准完成检查后，可从报告下载 PDF，或下载 Codex 交接材料。两种导出现在保留与网页一致的前后任务、源码与标准指纹、修改文件和复检结论。用户无需重新整理这部分信息；实际节省时间仍未测得。

## 用户怎么做

1. 在本地助手选择代码目录、页面和目标，完成第一次检查。
2. 修改该目录的代码，保持原页面地址与原检查标准，重新检查。
3. 打开报告，查看“本次复检”，下载 PDF；继续开发时下载 Codex 交接材料并主动附到对应项目对话。
4. 交接时同时保存复检关联 JSON 与原始证据。PDF 提供索引，不嵌入全部证据附件；下载材料不等于已经安装到 Codex 或产生长期记忆。

代码文件夹重新上传会产生不同快照；后续第 4 批已为基础静态网页接入明确同项目的复检选择，见 [快照复检](09-snapshot-repair.md)。

## 实际检查与修复

| 场景 | 结果 |
|---|---|
| 同目录实际改动、原标准不变 | 网页、PDF 和交接材料指向同一修复 |
| 连续下载且证据未变 | 返回相同 PDF 字节与指纹 |
| 重启后先下载，再改动原任务证据 | PDF 缓存失效，撤回修复确认；交接材料同步变化 |
| 原证据恢复 | 重新核对后恢复关联 |
| 同版本重复检查或改变标准 | 各自保留对应状态，不冒充修复 |
| 缺少版本指纹 | PDF 明确显示“未取得” |
| 历史帮助评估与修复结论 | 修正了笼统的“不是修复后的复检”表述，明确执行次数只属于本任务；跨版本结论单独查看 |
| 最终 PDF 文件 | 两份各 4 页，提取文字核对结论与指纹，全部页面渲染检查，无文字遮挡或截断 |

验证：69 项模块测试、9 个真实本机 API 与执行引擎场景全部通过。运行 `node audit/check-repair-workflow.mjs <新的输出目录> --exports` 可重现检查。01 号本地记录发现表述冲突，修正后的 02 号记录作为本轮依据。

范围仍为受控文字修复、同目录同页面及扫描文件。没有新增陌生项目迁移、真人省时或真实业务收益证据。原证据不合格时，当前任务自己的路径结果仍保留，但跨版本修复不再确认。已下载文件无法事后更新，证据变化后应重新下载。
