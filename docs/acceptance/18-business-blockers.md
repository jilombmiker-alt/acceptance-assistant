# 前置失败时，告诉用户先处理哪里

日期：2026-09-16。本批继续做深阅读清单的下一步建议，保持一个对话框。

原执行器已经能将前置未通过的后续路径标成受阻，本批没有复现“把受阻路径重复计成多个业务缺陷”。实际不足在于：新增失败、标记控件不匹配、下载未取得，都会收到相同的“先补齐导出证据”，用户仍要自己判断先处理哪里。

现在沿封存结果中的依赖关系找到前置环节，同一个检查项合并展示。只给出有证据的下一步，保留实际执行状态与未知。

| 受控故障 | 执行结果 | 现在告诉用户怎么做 |
|---|---|---|
| 点击新增后没有书目 | 新增 1 条偏差，后续 4 条受阻 | 先处理“新增书目”的已观察偏差，再复查受阻路径 |
| 标记按钮与计划定位不匹配 | 新增通过，标记 1 条未完成，后续 3 条受阻 | 核对“标记已读”的定位、页面状态和执行记录；导出内容仍未知 |
| 点击导出未触发下载 | 3 条通过，2 条导出未完成 | 核对导出控件、下载触发和运行条件，不直接认定导出内容错误 |
| 页面已读但导出未读 | 3 条通过，2 条导出偏差 | 保留真实文件差异，交给开发核对数据来源和状态映射；根因仍待确认 |

路径数不等于独立缺陷数。主指标是四种预设故障的下一步是否对应实际阻塞，同时不改变原状态；不是新增检查数、执行时间或真人省时。

## 用户怎么操作

看对话里的“下一步”，先处理点名的环节。需要依据时展开“为什么这样建议”，或打开报告查看位置、触发操作及记录文件。执行未完成时，优先核对运行条件和定位依据；需要复查时输入“重新检查”。对建议仍可采纳、拒绝或纠正，选择不算效果。

对话额外显示依赖受阻与执行未完成的路径数，避免将“0 条已观察问题”理解成全部通过。报告、PDF、Codex 交接使用同一条建议。诊断展示去除终端颜色控制符并限制长度，完整原始执行记录保留。

## 验收与限制

- 90 项模块测试通过，含前置追溯去重、依赖不足/循环保留未知、下载未完成、混合偏差与受阻、反馈、诊断转义和长度边界。
- 四个实际受控案例全部通过，使用新增、标记已读、筛选、导出、筛选后导出五条路径。正常和明确偏差路径各两次；未完成执行停止重放；受阻路径不执行。其余六条不在本批范围。
- 两个前置案例的操作记录被修改后，具体归因撤回为证据不足；恢复原字节再核对。没有把模型推测当成已证实根因。
- HTML 与 Codex 文案一致；两份实际 PDF 共 9 页，文字、指纹及每页排版均核对。前台实际查看了未完成数量、建议详情和报告；最终单对话截图检查通过。
- 中间一次运行因本机磁盘写入失败中断，未计通过；保留失败记录，完整重跑后才确认结果。

这是受控故障验证，不是独立准确性样本，不给出通用误报漏报率，也未覆盖任意依赖图、并发压力或整个产品。人工时间、返工收益未测得。

复现：`node audit/check-business-blockers.mjs <新的输出目录>`；加 `--pdf` 可生成两个前置案例的 PDF。公开[脱敏摘要](evidence/business-blockers.json)保留状态矩阵和建议；原任务、原始执行记录及 PDF 只留本地。
