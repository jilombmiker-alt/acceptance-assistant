# 业务建议、反馈与开发交接

日期：2026-09-16。范围：本地已审核阅读清单的导出检查。保持一个对话框；新增内容默认只显示下一步，依据按需展开。

## 用户怎么做

1. 完成检查后，查看一句下一步。点“为什么这样建议”了解影响、未知及复查条件；在报告中查看具体文件、操作、预期与实际。
2. 下载“把修改要求带回 Codex”，把交接文件附到开发任务。建议提供排查方向，不直接修改代码，也不授予新权限。
3. 需要回应时，在原对话输入“采纳建议：说明”“拒绝建议：原因”或“纠正建议：要求”。保存后可输入“查看结果”回到当前建议。
4. 修改实际代码后，按原标准重新检查。采纳不代表问题已修复，也不代表建议有帮助。

## 系统现在判断什么

| 条件 | 处理 |
|---|---|
| 有至少两次导出差异、下载文件及已保存证据均通过指纹核对 | 展示影响、位置、触发操作、要求来源、预期/实际和文件索引；建议核对数据来源及状态映射 |
| 缺下载、缺重复记录、执行未完成或证据未核对 | 改为先补证据；不根据缺文件猜测产品根因 |
| 用户拒绝 | 保存理由，不继续把原方向当作待执行建议；问题证据仍保留 |
| 用户纠正 | 保存当前任务下的纠正，提示先核对用户记录；不静默改原标准 |
| 用户采纳 | 记录选择，问题状态和效果均不因此变成通过 |
| 同目录同页面新任务 | 保留此前建议反馈为历史，注明不自动沿用；原任务记录仍存在 |
| 实际修改后原标准复检通过 | 当前已解决路径不再生成故障建议；单独保留修复关联，不宣称建议有因果收益 |

同一组导出异常会合并呈现排查方向，但明确说明尚未证明具体根因，也未证明这些路径一定是同一个缺陷。指导覆盖混合已读/未读、筛选后全部导出、刷新和改回未读后的实际 JSON，每条至少两次；缺项不能算通过。

## 验证与边界

80 项模块测试通过，包含缺封存、缺文件、重复次数不足、执行问题、反馈不改变结果、HTML 转义及无关路径不出建议。7 个真实任务审计环节通过，另外在实际单对话页展开说明、输入拒绝理由、刷新核对持久化并检查排版。

实测先发现 3 条受影响的导出路径；采纳后仍为 3 条，效果为未测得。开发工具实际修改副本并复检后降为 0，修复关联通过；拒绝、纠正、采纳历史仍保留。此顺序不证明建议导致修复，也不能估算人工省时。

本批接入 `/state`、`/business-advice.json`、HTML 报告和 Codex 交接。PDF 后续已接入新增业务建议与反馈，并通过独立文件验收，见 [PDF 验收](16-business-advice-pdf.md)。完整原始证据和反馈只保留本地；[公开摘要](evidence/business-advice.json)已脱敏。

复现：`node audit/check-business-advice.mjs <新的输出目录>`。`--inspect` 只供开发者停在故障结果页检查，检查完成需向该测试进程发送 SIGUSR1 后继续。

目前只支持本地已审核导出路径。历史展示最多沿用最近 20 条相关反馈；更早记录仍在原任务。不同项目、任意业务、任意上传快照、永久个人偏好、建议准确率和真人收益不在本批完成范围。
