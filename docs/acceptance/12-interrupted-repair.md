# 中断恢复后的复检证据

日期：2026-09-16。范围：本机、同目录同页面的基础静态网页检查；使用受控案例。

修复前实际复现：进程中断后重新启动工作台，原任务可继续并得到检查结果，但复检摘要仍显示“等待本轮执行和证据核对”。原因是恢复执行没有接入完成后的证据保存，且证据读取固定指向最初运行目录。

现在正常开始和恢复执行均接入完成处理。每次恢复使用独立运行目录和证据索引，保留此前检查点、已完成记录与旧索引。后续任务能引用恢复后保存的证据；原格式索引仍可读取。

| 检查 | 结果与边界 |
|---|---|
| 正常暂停再继续 | ✅ 不等待暂停任务结束才继续，原任务和授权不变 |
| 实际终止本测试工作台进程、重启、继续 | ✅ 识别原中断任务；保留已完成记录，补足原次数 |
| 中断后修改已扫描源码 | ✅ 拒绝混用旧检查点，提示重新建立任务 |
| 恢复后检查完成 | ✅ 原问题修复通过；7 条路径各保留 2 次记录 |
| 再次重启工作台 | ✅ 复检结论和恢复后的证据仍可读取 |
| 改动恢复目录中的既有记录 | ✅ 撤回通过，保留未验证；恢复原字节后重新核对 |
| 下一个任务引用本轮 | ✅ 可读恢复后的基线；源码没变则标为同版本重跑 |
| 旧格式与多次执行索引 | ✅ 模块验证兼容旧格式、不覆盖旧索引、拒绝越界目录和错配索引 |
| 上传快照服务自动重建、任意后端恢复 | ⏳ 未在本批验证 |
| 完成与保存之间发生崩溃 | ⏳ 仍需单独验证恢复策略，不宣称所有中断位置已覆盖 |

使用步骤：保持被测页面服务运行；用原状态目录重新启动工作台，查看原任务并选择“继续”。系统先检查源码和依据是否变化。需要修改代码时新建复检任务，避免把不同版本的结果拼到同一轮。恢复过程不增加用户审评表。

验证方式：`npm test`（74 项通过）；`node audit/check-interrupted-repair.mjs <新的输出目录>`。真实进程审计覆盖 9 个断言环节，原始证据保留本地。修改前观察可加 `--observe`，观察模式不代表修复通过。审计仅终止它自己创建的测试进程组。

这里证明的是连续复检与证据保存机制。没有测量真人节省时间、减少返工或泛化准确率；人工省时保持 `null`。本批未新增 UI 布局或 PDF 验收，不复用此前 PDF 检查充当新场景证据。
