# 修改代码后重新上传并复检

日期：2026-09-16。本地验证已完成；代码已发布到 GitHub（30bcb01），魔搭部署仍待完成。

已经完成基础网页检查的用户，修改静态网页后，在“检查我的产品”重新选择文件夹，并勾选“这是当前项目的修改版，按原标准复检”。系统带回原目标和明确文字，保留原输入、预期、范围、动作及重复次数。用户生成计划后，仍需开始本轮检查；不会沿用旧任务授权直接运行。

这个选择默认关闭。检查其他项目时保持不勾选即可。系统依靠用户明确声明建立快照关联，不通过同名文件夹或相似源码推断项目身份。误把无关项目声明为修改版，仍可能建立错误的身份关联，因此报告明确写出“用户确认同项目”。

## 已验证内容

| 项目 | 状态与证据 |
|---|---|
| 初次上传 | 独立检查，不编造前轮 |
| 完成任务后重启 | 原证据保留，重新上传可关联 |
| 选择同项目修改版 | 恢复原标准；生成新任务与本轮授权范围 |
| 新端口与新快照目录 | 只更新导航位置；验收文本里的 URL 不会被替换 |
| 实际修复 | 页面入口、明确文字、输入回读、尺寸检查 4 条路径，前后各执行 3 次；原文字偏差修复 |
| 同内容重新上传 | 显示同版本重复检查 |
| 未选择同项目 | 新任务独立，不套用旧标准与结论 |
| 旧任务 ID/版本、错误入口 | 拒绝关联 |
| 关联时另传新标准 | 拒绝悄悄替换，提示取消复检后新建任务 |
| 原上传内容 | 原快照保留，核对字节未改变 |
| 前台 | 实际浏览器核对默认未勾选、原目标恢复、只读状态、取消恢复新目标及按钮文字；查看上下区域排版 |

73 项模块测试通过；10 个真实本机 API 与执行引擎场景通过。复现：`node audit/check-snapshot-repair.mjs <新的输出目录>`。这是受控样例验证，不是陌生项目迁移或真人收益实验。

## 当前边界

- 只支持已完成、完成后未修改标准的基础静态网页任务；入口、文字、普通输入和尺寸检查。
- 报告下载/详情操作、业务模板、自动个人经验和历史模板任务暂不迁移；不能通过放宽原检查实现“通过”。
- 原控件被移除时仍保留原断言，不能用新页面发现的更少控件缩小标准。原控件移除的完整产品反例已通过核验，详见 [范围变化核验](11-repair-scope.md)；中断恢复后复检继续待验。
- 版本指纹仍只覆盖已扫描源码。项目身份是用户声明，完整产品质量、后台版本与真人省时未证明；省时保持未测得。

[公开脱敏摘要](evidence/snapshot-repair.json)。原始任务 ID、本机目录、执行记录仅保留本地。

## 复检草稿尚未执行时重启

当前版本生成、未修改且尚未执行的复检草稿，重启后可重新选择文件夹并勾选同项目，继续原标准；多次重传仍关联原已完成任务，草稿不算执行证据。改标准、缺原证据或旧草稿缺关联标记时不猜测恢复。[核验与使用步骤](21-snapshot-draft.md)。

重传会重新整理当前资源和输入定位缺项，补齐后旧提示可撤回；这不改变原检查动作和预期。[当前页面缺项核验](22-snapshot-observation.md)。
