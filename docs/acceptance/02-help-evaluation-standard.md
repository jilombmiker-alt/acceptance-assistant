# 个人历史帮助效果：审评标准与记录方法

版本：personal-help-v1，2026-09-13。公开整理版，描述产品评估机制，不包含任何人的能力评价。产品状态以 [迭代清单](../next-version/04-iteration-checklist.md) 为准。

核心问题：在达到相同最终验收要求的前提下，历史是否让用户少解释、少纠正、少重做，并且新增负担可接受？质量提高但更慢可以记为质量收益，不能直接宣称效率或净收益。

## 审评顺序

1. **结果门槛。** 实验前固定完整验收项及 critical / major / minor 影响分级，核对最终产物。两组使用同一组验收项，不以各自新增路径数作为分母。未验证、缺项、跳过及中止不算通过。
2. **主要收益。** 默认重点关注重复解释、纠错返工及用户实际操作时间；每批实验在执行前选定一个主指标和最小有意义改善值，不事后换指标，不使用加权总分。
3. **额外代价。** 单列用户操作、系统等待、模型及工具费用。历史整理、首次接入、维护和逐项确认时间计入用户操作成本；不可假定是免费或零成本。
4. **误用与复检。** 记录当前要求覆盖旧要求、一次性例外、无关历史、不足证据等情况。把同版本重复检查、修复后复检、下一任务中的复发区分开。

## 帮助用户的五个维度

| 指标 | 计数规则 | 不计作收益的情况 |
|---|---|---|
| 重复解释 | 适用历史已明确、但本次仍需用户重述的要求 | 正常提出新需求；后台提交次数；用户沉默 |
| 重复犯错 | 在固定验收项中，历史纠正过的问题再次出现的项数 | 同一问题重复跑两次算两个错误；未发现就推断无漏检 |
| 纠错返工 | 因误解既有目标或约束而推翻、重做的一轮工作 | 保存计划、普通意见或新增需求直接当作返工 |
| 不必要绕行 | 相对于预先定义的正确目标路径，多走的操作 | 总点击数、全部工具调用次数 |
| 人工盯守 | 为让任务正确继续而发生的提醒、追问和必要确认 | 将用户逐条批准经验当作免费操作 |

用户实际操作时间、系统等待时间分别测量，不与上述次数加权相加，避免同一负担重复计算。对话轮次作为解释指标保留，不能替代最终结果和纠错成本。

## 对照条件

A 使用当前完整请求、同等模型能力和通用检查，不提供个人历史；B 只增加相关个人历史。任务、初始请求、初始产物版本、模型配置、工具、预算及完整验收项应相同并保留指纹。

历史快照在两组执行前截断。标准冻结后，执行记录绑定标准指纹；更改标准需建立新的实验。不能用测试任务反向挑选历史后仍称为原先的对照。旧版“固定通用规则 A / 模型加历史 B”只能说明流程差异，不能隔离个人历史的作用。

真实用户连续做同一个任务会受学习影响。真人阶段应安排难度相近的任务并交替分组，或采用独立受试者及不知道分组的结果复核者；相近任务与完全相同任务的配对方法需要在研究设计中另行说明，当前严格相同任务判定器不自动认定不同任务等价。

## 判定

| 条件 | 输出 |
|---|---|
| 缺少公平条件、完整验收、已复核指标或证据 | 证据不足 |
| 两组最终结果合格，主指标改善达到预设值，成本在上限内，五个帮助维度均未恶化 | 本次有指标收益 |
| B 修复了 A 的验收失败，B 最终合格，且没有新增验收失败或历史误用 | 本次有质量收益；同时披露成本，超限时不认定净收益 |
| 新增验收失败、错误套用历史，或额外负担超出上限 | 本次有负面影响 / 额外负担超出约定 |
| 两组结果相同但主指标未达门槛，或最终目标仍未合格 | 尚未证明收益 |

当前版本对效率收益采用保守规则：任一帮助维度变差即不认定效率收益，不用减少解释抵消更多返工或盯守。时间和费用的可接受增加量由研究负责人在实验前按任务意义设定，不能凭本轮结果临时调整。数值没有跨场景通用的默认百分比。

所有输出限定到本次配对；受控标注、模型模拟用户和测试替身都不能升级成真人收益，单次真人收益也不能外推为长期收益。

## 产品内如何记录

工作台、网页报告和 PDF 使用同一套帮助效果摘要，包含最终结果状态、五个维度、执行变化、额外负担、复检边界和下一步。每条经验保留来源、适用理由、具体动作、执行结果、希望改善的维度、证据和下一步。

本轮已自动采集：成功的历史文本/反馈/修订接口提交次数、服务处理时间、可取得的语义调用时间及令牌用量、个人检查变化和执行证据。接口事件持久保存，刷新和重启不清零。新增反馈会更新 PDF 缓存版本。

**尚未自动测得：** 真人重复解释、返工分类、绕行、盯守、实际操作时间、实际等待区间、历史整理维护耗时、费用账单和完整结果验收。它们显示 `null / 未测得`，不能填 0。普通用户不需要逐项填审评表；当前离线研究由研究负责人组织记录和复核。

在“个人历史有没有帮上忙”下可下载 `/help-evaluation.json`，与当轮网页报告、PDF 和原始运行证据一起保存。

## 冻结标准与离线复核工具

代码：[帮助效果模块](../../v3/help-evaluation.mjs)；研究工具：[离线配对复核](../../scripts/evaluate-help-pair.mjs)。

先准备标准草稿 JSON：`criteria`（稳定 id 和影响级别）、`completeRubric`、`primaryMetric`、`minimumReduction`、`maxExtra`（userActiveMs/systemWaitMs/costMinor）、`currency` 和 `context`（taskHash/initialRequestHash/initialArtifactHash/modelConfigHash/toolsHash/budgetHash）。

在仓库根目录运行：

```sh
node scripts/evaluate-help-pair.mjs --freeze 标准草稿.json 冻结标准.json
node scripts/evaluate-help-pair.mjs --evaluate 冻结标准.json A.json B.json 新审评结果.json
```

冻结命令写入版本、时间及验收项指纹，并返回 protocolHash；文件存在时拒绝覆盖。两组执行记录使用相同 protocolHash/context，声明 arm、historyEnabled、startedAt、observationKind（human/controlled）、completed、currency、includesHistorySetupAndMaintenance；B 还需 historyCutoff/historySnapshotHash。

`acceptance` 为每个稳定验收项记录 id/status(pass/fail)/reviewed/evidence。`metrics` 的九项指标为 repeatExplanationCount、recurringErrorCount、correctionReworkCount、detourCount、supervisionCount、userActiveMs、systemWaitMs、costMinor、misappliedHistoryCount。每项须有 status=observed、value、reviewed=true 和非空 evidence 引用；计数须为非负整数，时间单位毫秒，费用为指定币种的最小单位。

`evidenceFiles` 用 id/file/sha256 索引每组记录目录内的本地证据。工具核对文件范围、指纹和证据引用，并把输入指纹写入输出；不覆盖既有结果。文件完整性不等于标注真实，研究负责人仍需复核误解、新需求、返工和最终产物的判定。该工具不会自动伪造真人日志，也不会把离线受控收益写进普通用户的真实任务摘要。

## 后续复检层级

- 单元层：检查判定边界、未测得处理和反例，证明程序按标准工作。
- 产品层：实际操作页面、提交反馈、下载 JSON/PDF、重启并核对记录，证明数据链路可用。
- 修复层：固定验收项，保留前后版本和产物，证明问题已修复；已支持本地同目录同页面关联，以及明确同项目的基础上传快照关联；[上轮问题入口](17-repair-history.md)可只读核对原标准与产物。任意业务快照迁移仍待支持。
- 用户价值层：新的适用任务 A/B、独立结果复核、真人行为与成本记录，验证是否节省。当前仍待开展。
