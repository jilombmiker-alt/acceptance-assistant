# 下一次 Web Coding 开发任务书

本文件为下一批开发任务定义，本次发布仅整理计划。完整愿景见 [产品框架](01-product-framework.md)，执行顺序见 [开发 SOP](03-development-sop.md)。

## 本批目标

在现有本地验收助手上，先完成“阅读清单的同一个导出状态错误，从发现到开发修改，再到按原要求复查”的连续证据链，并把本轮下一步建议做成有依据、可回查的结果。

保留未来跨品类架构，但本批不实现所有十二维、不接通任意线上业务、不同时加入 RAG、图像和真机。

## 使用场景

个人开发者准备交付阅读清单 Demo。原要求是能够新增、改阅读状态、筛选、刷新保留，并导出全部书目及当前状态。现有故障样例中，页面显示《山海笔记》已读，下载文件却为 read=false。

## 开发前核对

检查当前代码、现有任务入口与保存证据。部分文件保留旧阶段说明，不能直接把旧的“未实现”当成当前状态。确认本批真实差异后再改。

优先复用 inspect、planner、plan-validation、engine、authorization、task-control、report-journeys、help-evaluation 和 report-export。除非有具体原因，不另建一套执行引擎或结果格式。

## 本批功能

1. 为任务关联项目版本、明确要求、标准来源、范围、执行预算及稳定检查项 ID。
2. 运行现有业务案例，将实际下载文件与当前书目状态核对，保留首次和重复异常。
3. 在问题页给出：问题、位置、触发操作、对交付目标的影响和下一步；展开后显示预期、实际、文件与来源。
4. 下一步建议包括“交给开发核对导出数据来源和状态映射”，明确这只是排查方向，不能直接宣称根因。
5. 将问题、要求与证据导出为开发交接材料。修改仍由开发者/开发工具完成。
6. 以问题 ID、检查项 ID、标准版本和程序版本关联修改前后任务，原证据保留。
7. 在修复版本上复查原问题和相关输入状态，不把两个独立正常/故障样例冒充连续修复。
8. 用户可以对下一步建议纠正或拒绝，记录原因和后续结果。采纳不自动记为有效。

## 建议的规则结构

每个检查项具备以下字段，具体命名与现有 schema 对齐：

- 稳定 ID、用户要求及来源。
- 适用项目能力与交付阶段。
- 前置条件、输入和操作路径。
- 最终产物及独立预期来源。
- 判定方式、阈值来源与缺证据处理。
- 重复/观察/恢复策略及副作用限制。
- 维度、实际证据、结果状态和影响说明。
- 问题与后续复查的关联。

这些字段是设计要求，不直接作为现有运行器可执行的 JSON。

## 必须通过的验收场景

| 场景 | 预期 |
|---|---|
| 已读页面、未读导出 | 识别状态不一致，指向实际文件和操作 |
| 混合状态正常导出 | 对照当前全部记录，不误报 |
| 筛选后导出 | 依据本项目约定核对全部书目，不擅自改成仅当前筛选结果 |
| 导出文件无法取得 | 待判断/受阻，不记通过，不臆造内容 |
| 执行器找错控件 | 明确执行问题，不直接判业务缺陷 |
| 用户停用某条历史依据 | 新计划不继续应用，旧证据保留 |
| 原标准或程序版本变化 | 记录变化，防止用旧结果冒充新验收 |
| 同版本重复执行 | 显示重复检查，不称为修复成功 |
| 实际修改后复查 | 关联前后版本、同一标准及实际产物 |
| 证据不足以确定根因 | 给定位建议，明确未知，不编造修复原因 |
| 用户采纳建议 | 记录选择；实际复查通过后再记录处理结果 |
| 没有真人耗时与返工测量 | 显示未测得，不填 0，不估省时比例 |

随后用一个没有参与本规则编写的同类小型记录管理项目，检查迁移与接入成本。若缺少该材料，先完成上述现有案例，不用缺少新项目阻塞已授权实现。

## 产品体验

保留简洁输入入口。用户提供项目和已有材料，描述本次目标。由系统整理候选标准与计划；只对确实影响结果的冲突追问。页面默认展示范围、当前状态、问题和下一步，不要求用户填写十二维评审表。

## 交付

- 可运行入口和明确的支持范围。
- 连续修复案例，包含前后版本、标准、实际文件与结论。
- 陌生同类项目的验证结果，或明确说明尚未开展。
- 下一步建议的正例、缺证据反例和用户纠正记录。
- 仍未完成的能力及证据，单独保留。

## 后续批次

上述任务完成后，先完成陌生同类项目迁移和真实用户收益验证。达到预先约定的门槛后，再在 RAG 或商品图生成中选一类扩展。先取得真实结果、可复核标准和必要运行条件，再编写品类规则包。跨品类扩展以能力和证据为单位推进。
