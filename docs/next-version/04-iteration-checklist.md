# 版本迭代与验收清单

日期：2026-09-13。文档整理基于当前公开代码、本地记录以及本次对话中的线上验收结果；本轮不重新运行所有历史检查。✅ 仅表示写明范围已验证，⏳ 部分已有但闭环未齐，❌ 尚未取得完成证据，◇ 未来候选。

**开发顺序：P0 同一问题连续修复 → P1 陌生同类迁移 → P2 垂类真实收益 → P3 一种相邻能力 → P4 更多载体。**

当前聚焦 Web 记录管理工具的状态与文件一致性。框架保留广度，执行用以下证据门槛约束扩展。

| 确认 | 能力/交付项 | 当前做到了什么 | 下一步怎么做 | 如何验收 |
|---|---|---|---|---|
| ✅ | 公开应用、代码和视频 | 魔搭受控入口、GitHub 和 3 分半在线视频已发布；有提交成功回执 | P0：每次发布在实际域名回查 | 新访客可打开并完成受控任务 |
| ✅ | 单对话框与前台指引 | 已验证怎么开始、选择案例、生成 8 项计划、启动和查看结果 | P0：让陌生用户独立走查 | 记录完成率、求助点与实际投入 |
| ✅ | 阅读清单受控检查 | 线上故障版显示 1 项问题，正常版显示 0 项；代表路径分别重复两次有记录 | P0：保留该演示，增加不同状态输入 | 公开能力只限已验证样例 |
| ✅ | 受控报告修复对比 | 独立报告呈现案例：相同 5 项标准各两次，偏差 1→0 | P0：与阅读清单业务案例分开 | 不拼接为一个连续修复故事 |
| ⏳ | 阅读清单同问题连续修复 | 现有预置故障/正常版切换不构成连续修改证据 | P0：实际修改故障项目，记录变更、前后版本和导出文件 | 原问题按同一标准通过，相关导出状态无回归 |
| ⏳ | 验收契约与版本追溯 | 已有计划、指纹及部分记录机制 | P0：统一目标、标准、问题和修复关联 | 标准变更/同版本重跑/实际修复可明确区分 |
| ⏳ | 下一步建议 L1/L2 | 有任务控制、报告和局部下一步提示 | P0：补影响、证据、选项、未知及复查条件 | 缺证据时不编根因，采纳后依据结果复核 |
| ⏳ | 状态和错误归因 | 有部分受阻、未支持、异常与运行控制记录 | P0：统一产品偏差、执行器错误、缺条件等状态 | 前置失败不重复算成多个业务缺陷 |
| ⏳ | HTML/PDF 报告与交接 | 本地有报告导出和上下文交接模块，线上有报告入口 | P0：核对导出内容、版本、证据链接及交接完整性 | 生成文件可打开，内容与本轮结果对应 |
| ⏳ | 个人资料与历史适用 | 本地受控语义案例有来源到支持检查的映射 | P2：补失效、拒绝、当前要求覆盖旧要求与新任务复验 | 每条建议说明改变了什么；无关历史不应用 |
| ⏳ | Codex 日常使用 | 有本地上下文交接方式；没有自动全局记忆承诺 | P2：验证最少步骤的主动导入与范围撤销 | 接入负担计入收益，不能静默采集其他对话 |
| ⏳ | 助手自身操作边界 | 有受控目标、会话、跨站与局部授权检查 | P0：覆盖版本变化和异常请求；按范围独立复核 | 不能据此宣布被测产品权限与安全合格 |
| ❌ | 陌生同类项目迁移 | 未取得足够独立同类迁移证据 | P1：计划先用 3 个未参与规则编写的项目 | 逐项目报告覆盖、定制工作、接入和维护时间 |
| ❌ | 验收器独立准确性 | 受控复现不能给出通用误报漏报率 | P1：独立预标样本与盲审 | 报告样本数、误报、漏报、待判断和错误归因 |
| ❌ | 真实用户需求和持续使用 | 当前目标用户与使用频次仍是假设 | P0/P2：先 3 次访谈，再 5 人探索试用 | 真实任务、原有方案、后续使用意愿有记录 |
| ❌ | 真实省时、返工和成本收益 | 未测得，不能把测试耗时变化当人工节省 | P2：固定主指标，对照强基线 | 质量达标后比较净人工时间；完整成本均计入 |
| ❌ | 个人历史额外增益 | 有评估协议，尚无充分真人因果对照 | P2：同模型工具只改变历史条件 | 少解释/返工且不错误迁移；报告零增益与负结果 |
| ◇ | 自动影响分析与交付取舍 L3 | 当前不具备已验证的通用发布决策能力 | 当前垂类先试：原问题+相关路径回归建议 | 有依赖证据与责任人，系统不擅自降交付标准 |
| ◇ | RAG 或 AIGC 语义规则包 | 下一垂类候选，当前不作为承诺 | P3：当前垂类达标后只选一种 | 真实产物、独立标准、样本集和人工校准齐备 |
| ◇ | API、移动端、桌面与协作扩展 | 长期候选，现有局部证据不等于通用支持 | P4：按需求逐个接执行适配器 | 每种载体单独维护环境矩阵与回归证据 |
| ◇ | 十二维度完整支持 | 十二类是设计框架；增加分类不等于实现 | 随垂类需求逐项落地检查器 | 每项有适用判定、动作、结果和独立证据 |

## 下一批优先勾选

- [ ] 核对真实用户任务和原有检查办法，冻结本批主要假设。
- [ ] 在故障项目上取得同一导出问题的修改前证据。
- [ ] 由开发者/开发工具实际修改，并记录版本与变更。
- [ ] 按原标准检查混合状态、状态修改、刷新后、筛选后导出。
- [ ] 将问题 ID、标准版本、前后程序版本、文件和结论串联。
- [ ] 在缺文件、错控件、标准变化和无充分根因证据时正确保留未知。
- [ ] 交付一个可复述的完整案例和新一轮未完成清单。

## 效果怎样判定

| 评价层 | 主要指标 | 如何记录 | 不能替代它的数字 |
|---|---|---|---|
| 被测产品是否达标 | 必须项结果、实际产物、关联回归 | 冻结标准和版本逐项核对，缺项不算通过 | 页面点击数、执行完成、HTTP 200 |
| 助手判断是否可靠 | 误报、漏报、待判断率、错误归因 | 使用独立答案；列出分子、分母和不支持范围 | 新增检查项数、同一 AI 自评总分 |
| 用户是否少投入 | 净人工时间、纠错返工、重复解释 | 原有方式人工时间减去使用后的全部人工时间 | 系统执行耗时、总对话轮次 |
| 建议是否有用 | 正确后续处理、遗漏回归、额外返工 | 比较只有报告与报告加建议，追踪实际处理后结果 | 点击采纳、用户满意但无实际结果 |
| 历史是否有增益 | 适用条件补全、重复错误、额外解释与错误迁移 | 同等能力只改变历史；真人用匹配任务和交替顺序控制学习效应 | 引用历史数量、使用了模型 |

净人工时间必须包含：准备资料、接入配置、解释、误报处理、修改交接、复查和维护。等待与调用费用分别列示。没有测量填写“未测得”，不填 0。每批主指标和最小有意义改善值在实验前固定；不事后挑选更好看的指标。

## 扩展门槛与停止条件

| 阶段 | 继续的条件 | 未达到时怎么做 |
|---|---|---|
| P0 连续修复 | 同一项目的真实修改与原标准复查可追溯，相关路径没有已知回归 | 补证据或修复；保留现有演示，不称连续修复完成 |
| P1 同类迁移 | 计划 3 个陌生同类项目分别有独立结果和接入成本 | 先修规则包；高定制成本则收窄范围或考虑服务形态 |
| P2 垂类收益 | 预设质量门槛达标；探索试用显示有值得扩大验证的改善 | 无增益如实报告；若强基线更好，降低负担或做成插件 |
| P3/P4 扩类扩端 | 已有垂类门槛通过，有新任务需求、标准、产物和运行条件 | 继续做深当前垂类；不同时启动多类适配 |

3 个项目和 5 人试用是下一轮建议的探索规模，不是统计充分性保证。正式推广前需根据错误代价和观察结果扩大样本。
